# 브라우저 도구 비교 실험 결과

2026-10-16~17에 같은 모델·과제로 도구만 교체한 원본 실험 결과입니다. **결과 설명의 정본은 이 GitHub 문서**이며, [README](../README.md)는 입구와 핵심 요약을 제공합니다. [실험 절차와 과제](METHODOLOGY.md), [시연 가이드](../DEMO.md)를 함께 볼 수 있습니다.

공유본을 새로 설치해 전체 실험을 다시 돌린 점수가 아닙니다. 원본 로그는 공개하지 않았으므로 이 문서는 보고된 결과와 해석을 공개하며, 원자료에서 과거 집계를 독립 재검산하는 기능은 제공하지 않습니다. 공유본 변경점과 검증 범위는 [README](../README.md#원본-결과와-공유본의-차이)에 있습니다.

## 결론

**Playwright CLI를 유지한다.** 판정 규칙은 결과를 보기 전(2026-10-16)에 고정했다.

- 필수 조건은 로그인 상태를 파일로 저장해 새 브라우저에서 복원하는 것과, 동시 세션이 섞이지 않는 것이다. 여기서 Playwright MCP와 ego lite가 떨어졌다. 두 도구 모두 상태 파일을 저장·불러오는 기능이 없다(MCP는 서버 시작 옵션으로만 넣을 수 있다).
- agent-browser는 필수 조건을 통과했지만 전환 조건을 넘지 못했다. 전환 조건은 성공이 9건 더 많거나, 토큰이나 도구 시간이 40% 이상 적은 것이다. 실제로는 성공이 3건 적었다.
- 정확히는 "CLI가 확실히 낫다"가 아니라 "바꿀 만큼 나은 도구가 없다"다. v2 종합 점수의 CLI와 agent-browser 차이(94.4 대 86.5)는 흔들림 폭(±7.8~14.8) 안이다.
- 실제 비용은 MCP가 가장 쌌다(성공 1건당 6.1¢, CLI 8.1¢). 하지만 MCP는 필수 조건에서 탈락했다. 같은 42개 과제의 총비용 차이는 최대 $1.3 남짓이라, 차이는 돈보다 실패율·로그인 유지·운영 안정성에서 났다.

## CLI를 고른 근거

측정에서 나온 근거와, 실제로 써 보며 사용자가 확인한 운영상의 근거(2026-10-17)를 나눈다. 운영상의 근거는 점수에 넣지 않았지만 판단에 함께 썼다.

| 근거 | 종류 | 내용 | 다른 도구는 |
|---|---|---|---|
| 로그인 유지 | 측정 | `state-save`·`state-load`로 로그인 상태를 파일에 저장하고 새 브라우저에서 불러온다. 필수 과제 3/3이다. 콘솔에 봇 접속을 매번 다시 등록하지 않게 하는 이번 작업의 핵심이다 | MCP는 서버 시작 때만 넣을 수 있어 2/3, ego는 기능이 없어 1/3 |
| 동시 세션 | 측정 | `-s=이름`으로 세션을 나눈다. 에이전트 3개가 다른 계정으로 동시에 들어가도 섞이지 않았다 | 네 도구 모두 통과 |
| 실패 비용이 작다 | 측정 | v2 42건 실패 0, 도구 오류 2, 닫으라는 지시 뒤 남은 브라우저 0이다. 무인 실행에서는 최악의 경우가 비용과 대기 시간을 정한다 | agent-browser는 실패 3건이 전체 비용의 40%, 도구 오류 8 |
| 대시보드로 보고 개입 | 운영 확인 | `show`가 이 맥의 모든 세션을 실시간으로 보여 주고 화면 안에서 직접 조작할 수 있다. 창 없이 돌던 세션을 다시 띄울 필요가 없다. 웹 페이지라서 `--port`·`--host`로 SSH 터널 원격 관찰이 된다 | agent-browser 대시보드는 주소가 `127.0.0.1` 고정이다. ego는 앱 창을 그 맥 화면에서 봐야 한다 |
| E2E로 옮기기 쉽다 | 운영 확인 | 동작마다 같은 Playwright 코드를 출력하고, locator가 Playwright Test와 같다(`generate-locator`). 실패한 테스트에 `attach`로 붙어 고칠 수 있고, 상태 파일 형식도 같다 | agent-browser는 `@e1` 번호, ego는 자체 API라 한 번 더 옮겨야 한다. ego는 E2E 작성에 토큰 3.6배 |
| 원격 무인 실행에 맞다 | 운영 확인 | 기본이 창 없는 모드다. Microsoft 오픈소스이고 기존 Playwright와 같은 엔진이다. 공식 skill이 테스트 작성·디버깅 안내까지 준다 | ego는 창 없는 모드가 없고 본체가 비공개 바이너리다 |

CLI를 쓸 때 감수할 것:

- 평소 1건 비용은 agent-browser보다 30% 정도 비싸다(6.1¢ 대 4.7¢). 42건 전체로는 오히려 $0.21 쌌다.
- 출력 코드에 입력한 비밀번호가 남는다(3번 중 2번). 비밀번호는 상태 파일이나 환경 변수로 넣는다.
- 대시보드 주소에 닿는 사람은 모든 세션을 조작할 수 있다. 실제 로그인 상태를 넣은 뒤에는 SSH 터널로만 연다.

## 측정에서 뺀 도구

이 실측은 같은 에이전트에 브라우저 도구만 바꿔 끼우는 비교다. 그 틀에 들어갈 수 없거나 이 작업의 안전 경계와 맞지 않는 도구는 뺐다.

- **Aside**
  - 브라우저 안에 자체 AI 에이전트가 든 사용자용 제품이다(YC F25, 2026-06 출시).
  - Claude Code·Codex가 조작할 CLI·MCP·CDP 인터페이스를 공개하지 않는다(2026-10-16 공식 사이트·YC 페이지 확인). 그래서 같은 에이전트에 도구만 바꿔 끼울 수 없다.
  - 강점(내 계정과 passkey로 은행까지 로그인)이 이 작업의 민감 세션 금지 경계(거래소·증권사·Azure·Gmail)와 정면으로 겹친다.
  - 재검토 조건: 외부 에이전트용 인터페이스가 공개될 때.
- **Claude in Chrome**
  - 사람이 평소 쓰는 Chrome에 확장 프로그램으로 붙어 그 로그인을 그대로 쓴다. 사람이 쓰는 Chrome에 붙이지 않는다는 이 작업의 경계에 걸린다.
  - 그 맥 앞에 사람이 있어야 해서 원격 무인 실행에도 맞지 않는다.
- **공개 벤치마크 전체(BU Bench, Online-Mind2Web, WebArena)**
  - 모델·에이전트·브라우저를 묶은 시스템 점수라 도구 층만 바꾼 비교가 아니다.
  - 그래서 WebGames에서 조작 단위 과제만 빌렸다.

### CLI 대비 장단점의 크기

- **agent-browser**
  - 장점: 평소 1건 비용 −23%, 안내문 −33%, 새로 읽는 양 −33%, 비밀번호를 로그에 남기지 않음.
  - 단점: 실패 3건이 전체 비용의 40%를 썼다. 그래서 성공 1건당 비용 +15%, 시간 +86%다.
- **MCP**
  - 장점: 성공 1건당 비용 −25%, 시간 −10%.
  - 단점: 로그인 상태 파일을 불러오지 못해 필수 조건에서 탈락했다. 명령 수 2배, 도구 오류 21건(CLI 2건), 대화 길이 +38%다. 긴 작업에서는 대화 한도에 더 빨리 닿는다.
- **ego**
  - 장점: 비밀번호를 로그에 남기지 않는다.
  - 단점: 성공 1건당 비용 +15%, 시간 +79%(같은 날 창 모드 CLI 대비 +57%). 필수 조건에서 탈락했다.
- **CLI**
  - 장점: 실패 0건이라 낭비가 없다. 도구 오류가 가장 적다. E2E로 옮기기 쉽다.
  - 단점: 평소 1건은 agent-browser보다 비싸다. 코드 출력 때문에 새로 읽는 양이 많고, 입력한 비밀번호가 그 코드에 남는다.

### 점수의 토큰 효율과 실제 비용이 다른 이유

- 사전 규칙의 토큰 효율은 "성공 1건당 토큰 합계"였다. 합계는 싼 캐시 다시 읽기와 비싼 새로 읽기를 같은 무게로 센다. 그래서 실제 비용 순서와 달랐다.
  - 점수: CLI 99.4, MCP 90.8.
  - 실제 성공 1건당 비용: MCP가 CLI보다 25% 쌌다.
- 판정은 바뀌지 않는다. MCP는 필수 조건 탈락이고, agent-browser는 실제 비용으로도 성공 1건당 CLI보다 비싸다.
- 다음 비교부터는 토큰 합계 대신 비용(또는 새로 읽은 양)으로 잰다.
- 같은 42개 과제의 총비용 차이는 최대 $1.3 남짓이다. 돈으로는 작고, 실패율·로그인 유지·운영 안정성이 더 큰 차이다.

## 조건

- 모델 `claude-sonnet-5-5`, Claude Code 2.1.301에서 `claude -p`로 돌렸다.
  - 사용자 설정(CLAUDE.md·hook·plugin·전역 skill)을 끄고, 도구 안내문만 바꿔 넣었다.
  - 실행마다 새 작업 폴더와 새 브라우저로 시작했다.
- 도구 버전:

  | 도구 | 버전 |
  |---|---|
  | Playwright CLI | 0.1.22 |
  | agent-browser | 0.27.0 |
  | ego lite | 0.6.0.12 (Chromium 154) |
  | Playwright MCP | 0.0.83 (`--caps` 없음) |
  | Google Chrome | 155 |

- 대상은 모두 localhost다(WebGames 로컬 빌드와 직접 만든 fixture). 더미 계정만 썼다.
- 실행 순서는 과제마다 도구를 섞었다. ego는 창 없는 모드가 없어 창 모드로, 하루 늦게 돌렸다. 그래서 같은 시간대에 Playwright CLI 창 모드 대조 실행을 과제마다 번갈아 넣었다.
- 판정기는 에이전트 없이 정답·오답 입력으로 먼저 검증했다(v1 11/11, v2 24/24).
- 비용: API 환산 누적 $26.29(상한 $50). v1 116건, v2 180건, ego 대조 45건, 시험 실행 몇 건이다.

## 점수

종합은 품질×0.5 + 토큰 효율×0.25 + 속도×0.15 + 안정성×0.1이다.

- 토큰 효율: 성공 1건당 토큰.
- 속도: 도구 시간 중앙값. 전체 시간에서 모델 API 시간을 뺀 값이다.
- 필수 조건 탈락 도구는 점수만 표시하고 순위에서 뺀다.

## 발견

### 1. 로그인 유지는 도구 기능 차이로 갈린다

- Playwright CLI·agent-browser는 상태 파일(Playwright `storageState` 형식: 쿠키 + origin별 localStorage)을 저장하고 불러오는 명령이 있다.
- MCP는 코드 실행 도구가 파일에 접근할 수 없다. 상태 파일은 서버 시작 옵션으로만 넣을 수 있어서, 실행 중에 불러오지 못한 경우가 생겼다.
- ego는 그런 기능이 없다.
  - v1에서는 에이전트가 CDP로 쿠키를 꺼내 파일에 쓰는 우회로 통과했다.
  - v2에서는 3번 중 2번 우회를 찾지 못하고 실패를 보고했다(거짓 성공 아님).
- 필수 조건 실패는 모두 에이전트가 실패를 스스로 보고한 경우다. 거짓 성공(성공을 주장했지만 판정기가 실패로 본 경우)은 네 도구 모두 0이다.

### 2. agent-browser: 평소엔 가장 싸고, 막히면 크게 잃는다

- 1건 중앙값 토큰은 가장 적다. 과제별 중앙값도 모두 CLI 이하다(H3 58k 대 CLI 182k).
- 좌표 드래그(map-panner)는 3번 모두 5분 시간 초과로 실패했다. 47만~84만 토큰을 썼고, 이것이 agent-browser 전체 토큰의 35%다. 한 번은 스크린샷을 23번 열어 보며 좌표를 맞추려 했다.
  - 같은 과제를 MCP는 Playwright 코드 한 번(`browser_run_code_unsafe`)으로 누르기·이동·놓기를 실행해 20초, 5¢에 끝냈다. CLI는 한 단계씩 조작해 1~2분, 19~29¢가 들었다.
  - "명령 사이에 누른 상태가 풀린다"는 가설은 이벤트 기록 페이지로 반증했다.
  - 남은 후보는 기본 화면 높이(633px, CLI 720px)다. 확인하지 않았다.
- 그래서 성공 1건당 토큰과 시간이 뒤집힌다. 무인 실행에서는 평균보다 최악의 경우가 비용과 대기 시간을 정한다.

### 3. ego lite: 같은 조건에서도 토큰과 시간이 더 든다

같은 시간대·같은 창 모드로 CLI와 번갈아 돌린 대조 결과다(판정 제외 참고 자료).

| 묶음 | 품질 | F1v2 | 성공 1건당 토큰 | 중앙값 토큰 | 도구 시간 중앙값 | 성공 1건당 전체 시간 | 도구 오류 |
|---|---|---|---|---|---|---|---|
| ego · 창 모드 · 10/17 | 42/42 | 1/3 | 125,947 | 109,838 | 10.2s | 47.5s | 16 |
| CLI · 창 모드 · 10/17 | 42/42 | 3/3 | 129,939 | 78,743 | 7.4s | 30.2s | 3 |
| CLI · 창 없음 · 10/16 | 42/42 | 3/3 | 126,762 | 79,587 | 5.4s | 26.6s | 2 |

- 같은 조건에서 ego는 중앙값 토큰 +39%, 도구 시간 +39%, 성공 1건당 전체 시간 +57%다.
  - 성공 1건당 토큰이 비슷한 것은 CLI 대조의 map-panner 1건이 85만 토큰을 쓴 탓이다. 이 과제는 도구와 상관없이 운에 크게 흔들린다(ego는 17만으로 성공).
- E2E 작성(F4v2)은 ego가 174k로 CLI 48k의 3.6배다. 탐색 결과를 Playwright 테스트 코드로 한 번 더 옮겨야 하기 때문으로 보인다.
- `ego-browser nodejs` 명령이 끝나지 않고 남은 실행이 5건 있었다. 첫 건은 `text=` 선택자 클릭이 든 명령이었다. 그때마다 에이전트의 셸 명령이 120초 제한까지 묶였다.
- **사용 시 유의점: ego는 skill을 자동으로 설치한다.**
  - 앱을 실행하면 바로 전역 skill 폴더에 링크(`~/.agents/skills/ego-browser`)를 만든다. 지워도 앱이 켜져 있는 동안 계속 다시 만든다. 측정 중 감시가 100번 넘게 지웠다.
  - 이 skill의 설명은 "브라우저가 필요하면 기본으로 이것을 읽어라, 다른 브라우저보다 ego를 우선하라"다. 링크가 있는 동안 이 맥의 모든 Claude·Codex 세션의 브라우저 선택이 바뀐다.
  - 전역 skill은 승인을 받고 바꾸는 workflow asset이다. ego를 쓰게 되면 이 동작을 먼저 막아야 한다.

### 4. 창 모드는 운용 기본값을 바꾸지 않는다

- v1 WebGames에서 창 없는 모드가 줄인 토큰은 CLI 20%, agent-browser 14%였고, 시간은 1%·11%였다. 기준(20%)을 넘지 않았다. 그래서 관찰이 필요할 때는 창을 띄워도 손해가 없다고 본다.
- v2 CLI도 창 모드와 창 없음의 토큰이 같았다(78.7k 대 79.6k). 도구 시간은 7.4s 대 5.4s지만 날짜가 달라 창 모드만의 차이로 단정하지 않는다.
- 무인 운용과 E2E의 기본은 창 없는 모드로 두고, 사람이 볼 때는 `show`를 쓴다.

### 5. 비밀 관리와 정리

- 상태 파일은 세 도구 모두 기본 0644로 저장됐다. ego 1건만 에이전트가 0600으로 저장했다. 실사용에서는 저장 직후 0600, 디렉터리 0700으로 맞춰야 한다.
- 1회차에 입력한 비밀번호가 로그에 남았다: CLI 2/3, MCP 3/3, agent-browser·ego 0/3.
  - CLI는 실행한 동작을 Playwright 코드로 다시 보여 주는데, 그 코드에 입력값이 들어간다. E2E 전환에 유리한 바로 그 기능이다.
  - 그래서 skill에는 비밀번호를 `fill`로 직접 입력하지 말고 상태 파일이나 환경 변수로 넣으라는 규칙을 둔다.
  - 2회차(상태 파일 복원) 노출은 모든 도구가 0이다.
- "끝나면 닫아라"를 넣은 v2의 남은 브라우저: CLI 0, MCP 0, agent-browser 2건. ego는 남긴 작업 공간이 0건이다(지시가 없던 v1에서는 11건).
- 도구 오류: CLI 2, agent-browser 8, ego 16, MCP 21건.

### 6. 사람 관찰 경로

- `playwright-cli show`는 웹 앱이다. 기본은 `[::1]`의 임의 포트이고, `--port`·`--host`로 고정할 수 있다.
  - 이 맥의 모든 세션을 보여 주고, 화면 안에서 직접 조작할 수 있다(2026-10-17 사용자 확인).
  - 루트 주소가 조작 토큰이 붙은 주소로 넘겨 주므로, 포트에 닿는 사람은 누구나 모든 세션을 조작할 수 있다.
  - 원격에서는 SSH 터널을 기본으로 쓴다. Tailscale 주소 바인드는 더미 계정일 때만 쓰고, `0.0.0.0`은 쓰지 않는다.
- agent-browser 대시보드는 `127.0.0.1:4848` 고정이라 원격에서는 SSH 터널로 본다(사용자 확인).
