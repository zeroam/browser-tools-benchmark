# 비교 실험 절차와 테스트 목록

[README](../README.md) · [실측 결과](RESULTS.md) · [CLI → E2E 시연](../DEMO.md)

## 목적과 비교 범위

AI 에이전트의 개발·검증 작업에 맞는 브라우저 도구를 고르는 실험입니다. 화면 탐색·값 대조·E2E 작성의 정확성에 더해, 원격 무인 작업에서 필요한 로그인 유지와 동시성을 평가합니다. 모델 성능을 비교하는 실험은 아닙니다.

비교 대상은 Playwright CLI, agent-browser, Playwright MCP, ego lite입니다. 기본 실행 명령은 ego를 제외한 세 도구를 사용합니다. ego는 전용 macOS 계정과 명시적 설정이 필요합니다. 설치·버전·예산 명령은 [README의 재실행 절차](../README.md#원본-도구-비교-실험-재실행)에 있습니다.

`bench.py demo --parallel`은 관찰용으로 v1·v2 각각 한 브라우저 세션을 유지합니다(F1 재시작·F2 보조 세션 예외). 이 페이지의 원본 측정 조건과 구분합니다. `--fresh-sessions`를 붙이거나 기존 `bench.py run`을 사용하면 과제별 새 브라우저 정책을 유지합니다. 고정 세션 시연의 창 모드·시간·메모리·안정성은 원본 벤치마크와 직접 비교하지 않습니다.

WebGames의 모든 과제를 사용하지 않습니다. 브라우저 조작을 대표하는 기본 10개와 어려운 10개를 골랐습니다. 퍼즐·CAPTCHA처럼 모델의 추론이나 외부 조건을 강하게 측정하는 과제는 이 실험의 목적에서 벗어납니다. 선정은 전체 WebGames를 대표하는 통계 표본 추출이 아니므로 선정된 과제의 결과로 해석합니다.

## 실행 절차

1. **조건과 판정 규칙을 먼저 고정합니다.** 원본은 `claude-sonnet-5-5` 하나로 실행했습니다. 과제, 기대 결과, 반복 횟수, 점수 비중, 필수 조건, 전환 기준을 결과 확인 전에 정했습니다.
2. **로컬 대상을 준비합니다.** WebGames production build와 자체 fixture 서버를 띄웁니다. 계정·표·봇 데이터는 모두 더미입니다. 버전은 `bench.py versions`, 스케줄은 `schedule`·`schedule-v2`로 기록합니다.
3. **도구별 실행 환경을 분리합니다.** 새 작업 폴더·새 브라우저를 사용하고, Claude Code의 모델·프롬프트 틀·허용 도구를 맞춥니다. 도구별 공식 안내와 MCP 설정은 달라집니다. 사용자 설정·전역 skill이 비교에 섞이지 않게 제한합니다.
4. **과제별로 도구 순서를 섞어 실행합니다.** v2는 각 과제를 도구당 3회 수행합니다. ego는 원본에서 하루 늦게 창 모드로만 실행했으며, 같은 시간대의 CLI 창 모드 대조 실행을 별도로 넣었습니다.
5. **에이전트가 결과를 제출합니다.** 일반 과제는 `ANSWER: ...`, E2E 과제는 `e2e/positions.spec.ts`를 제출합니다. 소스·정답 파일 읽기로 답을 찾는 지름길은 금지합니다.
6. **실행기가 제출물을 판정합니다.** 정답과 서버 기록·상태를 대조하거나, 제출한 테스트를 정상 앱과 버그 앱에서 실행합니다. 성공 주장과 판정이 다르면 거짓 성공으로 기록합니다. 지름길 의심 로그는 검토 대상입니다.
7. **실행 단위 지표를 기록하고 집계합니다.** `runs/<ID>/meta.json`에서 판정, 토큰, API 환산 비용, 시간, 오류, 잔여 브라우저를 확인합니다. `score.py`와 `score_v2.py`가 보고서를 생성합니다. 필수 과제나 비교 대상이 부족하면 선택 판정은 보류합니다.

일반 AI 호출의 제한은 5분·$1이며 E2E 작성은 10분·$2입니다. F1은 저장과 복원을 위한 두 번의 호출, F2는 세 에이전트의 동시 호출을 포함합니다. 따라서 스케줄 항목 하나와 모델 호출 하나는 다릅니다. 상위 예산은 완료 로그 기준의 실행 전 검사이며 실제 과금의 강제 상한은 아닙니다.

## WebGames v1: 기본 조작 10개

실제 목록과 과제 프롬프트의 입력은 [webgames-tasks.json](../webgames-tasks.json)입니다. 이 파일에는 판정용 정답도 있으므로 실험 중 에이전트에게 읽히지 않습니다.

| 과제 | 보는 조작 |
|---|---|
| ButtonMegastar (`buttons`) | 버튼 클릭 |
| TodaysDate (`date`) | 날짜 입력 |
| FileUpload (`file-upload`) | 파일 업로드 |
| FileCredentials (`file-credentials`) | 파일 다운로드 후 내용에 따라 로그인 |
| KeyCombo (`key-combo`) | 키 조합 |
| MenuNavigator (`menu-navigator`) | hover로 하위 메뉴 열기 |
| CanvasCatch (`canvas-catch`) | 캔버스 드래그 |
| IframeNest (`iframe-nest`) | 중첩 iframe 내부 조작 |
| TabSync (`tab-sync`) | 여러 탭 사이 이동·값 연결 |
| RightClickReveal (`right-click`) | 우클릭 메뉴 |

기본은 각 1회입니다. `buttons`, `file-upload`, `iframe-nest`는 도구당 2회를 추가해 총 3회로 편차를 봤습니다. CLI와 agent-browser는 10개 과제를 창 모드로도 한 번씩 실행합니다. v1은 모든 도구의 품질이 포화돼 더 어려운 v2를 추가했습니다.

## WebGames v2: 어려운 조작 10개

실제 목록은 [webgames-tasks-v2.json](../webgames-tasks-v2.json)이며 도구당 각 3회입니다.

| 과제 | 보는 조작 |
|---|---|
| OTPEntry (`otp-entry`) | 숫자 입력 후 자동으로 옮겨가는 포커스 처리 |
| TextMirrorHard (`text-mirror-hard`) | 공백을 포함한 정확한 텍스트 입력 |
| ScrollHorizontal (`scroll-horizontal`) | 내부 영역의 가로 스크롤 |
| PopupChaos (`popup-chaos`) | 겹쳐 가려진 팝업과 동명 닫기 버튼 처리 |
| ButtonHold (`button-hold`) | 버튼을 누른 채 유지 |
| ClickPixel (`click-pixel`) | 작은 대상의 좌표 클릭 |
| SliderSymphony (`slider-symphony`) | 슬라이더 조작 |
| PrintReveal (`print-reveal`) | 인쇄/PDF 흐름 |
| MapPanner (`map-panner`) | 좌표를 맞춘 지도 드래그 |
| RightClickRevealHard (`right-click-hard`) | 어려운 우클릭 메뉴 조작 |

v2 성공은 정답과 서버의 완료 기록을 함께 확인합니다. OTPEntry에는 붙여넣기 성공 경로가 완료 이벤트를 남기지 않는 예외가 있습니다. 이 경우 정답이 도구 출력에 실제로 보였고 소스 유출 의심 표시가 없는지를 추가 확인합니다. 해당 예외는 `WG2_NO_COMPLETION_OK`와 `run_wg2`에 구현돼 있습니다.

## 자체 fixture: 실제 개발·검증 흐름

fixture는 작고 통제 가능한 테스트용 웹 앱입니다. [fixtures/server.py](../fixtures/server.py)가 제공하고 [bench.py](../bench.py)가 실행별 데이터와 정답을 생성합니다.

| 과제 | 절차 | 성공 조건 |
|---|---|---|
| F1 로그인 유지 | 더미 접속 정보를 등록하고 상태 저장 → 기존 브라우저 종료 → 인증 정보를 주지 않은 새 호출에서 복원 | 재로그인 없이 자기 코드를 읽음; v1 도구당 2회 |
| F1v2 로그인 유지·노출 | F1을 반복하면서 저장 상태로만 복원 | 올바른 코드, 재로그인 없음, 2차 실행의 비밀번호 노출 없음; 3회. 1차 노출은 별도 기록 |
| F2 동시성 | 같은 origin에 서로 다른 더미 계정으로 에이전트 3개 동시 접속 → 새로고침 후 재확인 | 셋 모두 자기 코드와 계정 유지; 2회 |
| F3 콘솔 확인 | 봇 목록 → 지정 봇 상세 → 기대값과 포지션 표 대조 → 스크린샷 | 심어둔 불일치 1개를 정확히 보고, 허위 차이 없음, 스크린샷 있음; 2회 |
| F4 E2E 작성 | 브라우저로 탐색하고 Playwright Test 작성 | 정상 앱 통과, 값 변경·잘못된 이동 앱 실패; 2회 |
| H1 큰 표 | 400행 표를 기대 CSV와 비교 | 심어진 불일치가 2개·0개·3개인 세 실행에서 누락·허위 보고 없이 대조 |
| H2 긴 흐름 | 봇 5개 × 탭 3개와 대화상자를 탐색 | 요구한 20개 값을 정확하게 수집; 3회 |
| H3 변하는 화면 | 무한 스크롤의 173번째 항목, 5초 뒤 사라지는 토큰, 2.5초마다 다시 그려지는 버튼 조작 | 해당 실행에 생성된 정답 코드와 일치; 3회 |
| F4v2 E2E 작성 | 탐색 후 행 수와 모든 셀·이동을 검사하는 테스트 작성 | 정상 1회와 2.5초 지연 정상 3회 통과, 버그 6종 모두 실패; 도구당 3회 |

F4v2의 버그 6종은 다음과 같습니다.

| mode | 심는 버그 |
|---|---|
| `bug-value` | 포지션 수량 변경 |
| `bug-side` | LONG/SHORT 방향 변경 |
| `bug-extra` | 행 추가 |
| `bug-missing` | 행 누락 |
| `bug-nav` | 클릭한 봇과 다른 상세 열기 |
| `bug-404` | 상세 API 오류 응답(이름과 달리 구현은 HTTP 500) |

빠른 `demo.py verify`는 미리 작성한 기준 테스트를 정상·지연 정상 각 1회와 버그 6종에 실행하는 **8종 검사**입니다. 모델이 테스트를 직접 작성하는 F4v2의 10회 앱 검증과 구분합니다. 빠른 시연은 AI 비용 없이 검증 개념을 체험하고, 비교 실험은 AI가 작성한 결과의 품질과 비용을 측정합니다.

## 실행 횟수와 점수의 분모

원본 기록은 v1 116항목 + v2 180항목 + ego와 같은 시간대 CLI 창 모드 대조 45항목 = **341항목**입니다. 시험 실행은 별도입니다.

- v1 116항목: 도구 4개 × (WebGames 10개 + F1~F4 각 2회 + 대표 WebGames 3개 각 2회 추가) = 96항목, CLI·agent-browser 창 모드 20항목 추가.
- v2 180항목: 도구 4개 × (WebGames 10종 + H1·H2·H3·F4v2·F1v2 5종) × 3회.
- v2 **품질 42건/도구**: WebGames 30 + H1·H2·H3·F4v2 12. F1v2는 별도 필수 조건이고, F2는 v1 결과를 함께 사용합니다.
- 기본 `schedule`·`schedule-v2`는 v1 116개·v2 180개를 생성합니다. 원본의 추가 대조 45개는 기본 생성 스케줄에 포함되지 않습니다. ego를 제외하거나 일부 ID만 실행하면 실제 실행 수는 줄어듭니다.

## 지표와 선택 규칙

| 지표 | 의미 |
|---|---|
| 품질 | 제출물의 실제 성공 비율 |
| 거짓 성공 | 에이전트는 성공이라고 했지만 판정기가 실패로 확인한 경우 |
| 토큰 효율 | 성공 1건당 토큰 합계. 캐시 읽기와 신규 입력은 금전 비용이 달라 별도 비용도 함께 확인 |
| 속도 | v2는 전체 시간에서 모델 API 시간을 뺀 도구 시간의 중앙값. v1 집계 코드는 전체 시간 중앙값을 사용 |
| 안정성 | 도구 오류·재시도·종료 후 잔여 브라우저 등 |
| 비용 | Claude Code가 보고한 API 환산값. 구독의 실제 추가 청구액과 구분 |

종합은 품질 50% + 토큰 효율 25% + 속도 15% + 안정성 10%입니다. 로그인 복원과 동시성은 점수와 분리한 필수 조건입니다. v2는 F1v2 3/3과 F2 2/2가 필요합니다.

원본의 기본 선택은 CLI 유지입니다. 대안이 필수 조건을 통과하고, v2 품질 성공이 9건 더 많거나, 성공 수가 같거나 더 많으면서 중앙값 토큰 또는 도구 시간이 40% 이상 줄어야 전환을 제안합니다. 거짓 성공이 더 많으면 전환 후보에서 제외합니다. 차이가 측정 편차보다 작으면 확실한 우열로 보지 않습니다. 점수와 실제 선택 규칙은 별도입니다.

## 결과를 읽을 때의 한계

원본은 단일 모델·localhost·소수 반복입니다. 선정한 테스트에서의 정확성과 운용 적합성을 평가하며, 외부 사이트 전체·다른 모델·CI 환경을 대표하지 않습니다. ego의 날짜·창 모드 차이는 대조 실행으로만 확인했습니다.

공유본은 세션 분리와 정리 방식을 바꿨고 전체 341항목을 재실행하지 않았습니다. 역사적 수치는 [RESULTS.md](RESULTS.md), 공유본의 실제 검증 범위는 [README](../README.md#공유본-검증-2026-10-21)가 소유합니다. 원본의 상세 로그는 공개하지 않으며, 소스 기반 지름길 감시는 자동 sandbox가 아닙니다.
